# P10：开服、编辑器、重连补发与运行加固

更新于 2026-09-14。此记录覆盖开服、编辑器／牌组范围校验、卡组删除、加入者自选卡组和可配置构筑／疲劳。当前格式已统一，移除本地协议升级、场地字段别名及不携带逐卡清单的准入路径。P10 整体尚未结束，剩余项见 ImplementationPlan。玩家规则见 [当前玩法指南](../GameplayGuide.zh-CN.md)。

## 玩家操作

1. 卡牌编辑：进入“卡牌编辑器”，选择现有卡或新建。基本属性页加入四周留白和更宽行距；耐久即强度，只保留一个输入框，永久场地禁用此框。禁止本路主动攻击、蓄能、关键词和充能触发统一放在“效果 JSON”对象中。保存写入独立草稿包，页首可导出单卡（含关联衍生卡／文字）或整个内容包；内容包管理可按 ID 导入合并、启用和切回内置包。
2. 本机开服：选择房间名、1024–65535 端口、自己的参考牌组、对战协议及提交时限（不限时／30／60／120／180 秒）。不需要知道或配置对手牌组，对方加入时自行选择。时限同时用于换牌和每回合规划；默认不限时、仅监听本机，勾选局域网后对外监听。点击启动，再使用“自己加入”或复制对应席位的完整邀请地址。
3. 加入对战：粘贴邀请，选择自己的牌组，先“核对房间”，可查看完整玩法协议。再确认协议与牌组，等待双方确认后自动进入战场。房主建议牌组出现在牌组下拉框中，玩家可以选其他合法牌组；已经确认的牌组在本局锁定。
4. 停止／恢复：开服页停止会断开所有参与者。恢复上次房间重新读取原协议、原规则、原时限、已锁定牌组及日志。留在战场的客户端自动重新连接并取当前快照；返回大厅后可再次使用原邀请加入。恢复不会重新抽牌或使用菜单中新改的规则替换旧局。
5. 限时对局：战场左侧显示服务器提交倒计时。换牌到期保留所有未确认手牌；规划到期保留已经部署的牌并自动提交。暂停／倍速仅作用于表现动画，不能暂停对局计时。
6. 断线与诊断：短暂断线后自动补播未收到的战斗帧；历史不可用时直接恢复当前战场。联机战场上方“导出诊断”保存到 `user://diagnostics/`，断线时也能导出本机记录；文件可用于排查同步问题。
7. 删除卡组：牌组工坊自建卡组及新建草稿右上角显示“删除”，确认后移除对应保存文件及草稿；取消保留。内置默认模板保持可用，重命名写回原保存标识。
8. 配置规则：对战协议的“构筑与疲劳”中调整精确总张数、每种已选卡最少副本和最多副本；职业规则可选正常／仅本职业／不限职业，均为基础卡。疲劳可选不疲劳／1、2、3…逐次递增／即死。卡组编辑器自动读取当前协议，原卡组不合法条目标红供修正，不静默删卡。

## 本轮构筑与疲劳

总张数为 1–256，副本下限为正且不超过总张数，上限不低于下限且不超过 256。牌库真正为空时才触发疲劳，双方各自计数，效果抽牌与新回合抽牌共用该计数。满手时抽到真实卡仍烧牌，空抽仍按疲劳规则；非空牌库的筛选失败、生成卡牌不计疲劳。同帧双方死亡为平局，断点和回放保留疲劳次数。

疲劳计数进入权威状态、公开投影和检查点，协议绑定当前状态格式，菜单、房间与回放统一严格校验。内部测试期只维护当前格式，源码、文档、开发回放夹具和生成产物同步更新；不保留字段别名或自动升级入口。详见 [ADR-029](../ADR/029-configurable-decks-and-fatigue.md)。

## 防止客户端私改卡牌的边界

服务器从本地房间配置编译自己的规则包并锁定 RuleContentHash／ProtocolHash。每位玩家提交自己的职业、卡牌 ID、数量及逐卡规则哈希，服务器独立执行 MatchFactory 构筑校验：总张数、单卡份数、重复 ID、卡牌存在性、基础／衍生来源、职业限制。仅要求双方对“两个卡组并集及其递归规则引用”拥有一致定义，未参与本局的卡牌允许不同、缺少或额外存在，不要求全卡池相同。

第二位确认时会重新验证第一位对新增卡牌的定义，失败则不写入第二份准入、不开始对局；同步对应卡牌后可用原锁定牌组重试。恢复时再次检查双方清单。清单不上送数值与效果，房间描述不公开对手牌组或引用闭包。准备报文限 512 KiB／2048 项，普通 WS 命令仍限 64 KiB。无论全包哈希是否相同，缺少逐卡清单都拒绝准入。规则及导出闭包共用 CardRuleScope，详见 [ADR-028](../ADR/028-field-durability-and-deck-rule-scope.md)。

双方确认前不存在可操作的 MatchActor。确认请求只有房间准入 DTO，额外的 attack／health／effects 等字段被严格 JSON 合同拒绝。战斗命令也只引用服务器分配的手牌实例 ID；实际数值与效果来自服务器冻结的定义。客户端即使谎报正确哈希，也不能通过报文给服务器添加数值或卡牌实现。

玩家一、玩家二和观战分别使用 256 位随机凭据，服务器配置只存凭据 SHA-256；托管客户端的私有 last-room 文件保存完整邀请以支持恢复。邀请的 token 位于 URI fragment，HTTP／WS 适配器转入 Authorization 头，不作为查询参数发送。只修改 audience 无法换座；观战没有私有手牌与提交权限。WS 在已鉴权基础上再次核对协议哈希与规则哈希。

该功能检查规则一致性与构筑合法性，不自动判定“超模”。双方针对本局使用相同自定义定义即可对战。WS／重连中的全包哈希用于绑定服务器冻结的房间内容，不要求玩家本地整个包相同。仍信任房主运行的权威服务器程序；没有引入第三方可信服务器或远程程序证明。

## 托管与存档

- `LocalServerLauncher` 运行独立 self-contained Host，禁止 shell 执行，直接传入参数；以健康接口的唯一 matchId 验证就绪，避免将端口上的其他服务当作新房间。
- 关闭时先通过私有 stdin 请求正常退出，超时只结束自己持有的进程树。启动器崩溃导致 stdin EOF 时，Host 也停止。房间名不作为目录或命令使用。
- 玩家确认写入原子 admission 文件，规则快照在 room.json 中；这两个文件与命令日志属于服务器私有数据，不通过观察者接口提供。
- 每个处理后的权威命令及 ACK、结果状态哈希进入带序号和前驱哈希的 JSONL 日志。flush 到磁盘后才发送 ACK／视图；重复命令直接返回原 ACK，不重复执行。
- 每 16 条记录写入完整原子检查点。重启核对日志哈希链、检查点所指日志位置和状态哈希，再回放尾部命令并逐条核对结果；恢复席位范围的命令去重缓存。
- 结算在同一次 mailbox 操作中完成并持久化，然后发布表现帧。结算期间崩溃恢复到最后已持久化的命令边界，未 ACK 的命令可以重试；已开始发布的帧对应的最终状态已经落盘。短暂断线可在有限观察记录内补发，服务器进程重启不恢复历史表现窗口。
- 日志／检查点损坏时写 quarantined.txt 并拒绝打开，原始证据不被覆盖。单局存储失败关闭该局观察者，不影响其他 Actor。
- 默认邮箱 64、观察者缓冲 512、观察者数 32、近期命令键 4,096；WS 报文 64 KiB、每连接每秒 60 条，完整分片消息最多 5 秒；房间端点按 IP 每分钟 180 次。日志分段／恢复根各有 128 MiB 读取上限，默认每 512 条压缩一次。

## 自动重连与服务端时限

远程 DesktopSession 拥有独立的邀请凭据和 HTTP 客户端；每 10 秒请求心跳快照，心跳最多等待 5 秒，普通请求最多等待 15 秒。断开后重连单次最多 12 秒，失败按 2／4／6／8／10 秒退避；用户返回大厅或退出会取消循环。临时 5xx／429 可重试，凭据或协议校验失败停止重连。重新连接必须保持原 RuleContentHash、ProtocolHash、RoomSettingsHash、席位和不小于原快照的 revision。第三批增加有限帧补发；旧连接关闭与重建期间不再重复向已销毁客户端请求同步。

提交在确认报文丢失时，使用同一个命令 ID 和原 expected revision 重试。服务端先恢复持久化去重缓存再接收命令，已接受操作返回原 ACK，不重复出牌；如果原操作未到达而期间已超时，则返回 revision 拒绝，不把旧规划套到新回合。

RoomTiming 可独立设定换牌／规划秒数（0 或 5–3600）；游戏开服页提供相同的两阶段时限。RoomSettingsHash 绑定规则哈希、玩法协议哈希和两项秒数，所有房间的 ready 和 WS 均要求确认该哈希。第一次核对后的规则、协议或时限发生变化，客户端拒绝自动接受。

Host 每 250 ms 调度一次房间时钟；首次观察到新阶段时生成 deadline.json，先原子保存再发布倒计时。后续部署、心跳或重新连接不延长该截止时间。命令到达 Actor 时也检查已安装的截止时间，避免客户端抢在下一次调度前越过到期时间。恢复沿用已写入的截止时间；离线期间过期的阶段立即补交，随后新阶段获得完整时限，不按离线时长连续跳过多轮。尚未被调度器记录的新阶段在恢复后的首次调度开始计时。

到期按固定席位顺序，仅为尚未提交的玩家生成 SystemTimeoutCommand，包含回合、阶段和玩家 revision。Kernel 不访问时钟；它检查上下文后执行保留换牌／提交当前规划的确定性逻辑。系统命令有独立日志标记、进入规范命令日志和检查点，恢复时不污染客户端命令去重键。桌面回放及 CLI 识别相同命令。

倒计时作为仅服务端可发送的 MatchTimerPayload 发布，不进入状态哈希；客户端用服务器剩余时长和本机单调经过时间显示，避免依赖客户端日历时钟。阶段切换和结束会清除旧计时，最后 10 秒提示变色。时钟文件损坏或调度持久化失败会使该局关闭，不能悄悄变为无限等待。

## 第三批：补发与长期运行边界

每个 audience 分开保存至多 128 条观察记录且不超过 1 MiB，记录命令快照和表现帧，断线期间继续记录。重连携带最后已接收的 match revision／observer hash；服务器只在当前鉴权席位的记录中匹配。匹配成功返回基准投影、遗漏表现帧和当前投影，整包仍受 1 MiB 消息上限约束；超窗、错误席位、未知哈希、过大报文均回退当前快照。ACK 和墙钟倒计时不补播；当前计时单独同步。已经接收到客户端但尚未播放的旧动画不属于网络补发范围。

ObserverStore 对整个补发批次的哈希、席位、协议／规则、帧号严格递增和容量一起校验，通过才更新权威视图并交出表现队列。GameApp 从基准投影重建，按普通动画路径消费补发帧，结束后显示当前视图；非法批次不展示其中一部分。服务器重启只保留当前恢复态，无历史窗口；游标若正好等于当前状态可返回空补发。

FileMatchJournal 默认每 512 条处理记录形成 `journal-head.json`：保存初始状态哈希、房间 ID、最新序号／链哈希、完整检查点和近期非系统命令。恢复根原子提交后，再原子替换 `commands.jsonl` 为空分段；若在两步间退出，启动时校验并跳过已经被恢复根覆盖的前缀。首次压缩前尚无恢复根，从当前检查点和完整日志恢复。近期命令去重默认 4,096 条，运行中和重启后均有界；窗口内重试返回原 ACK，窗口外重试重新经过玩家 revision 校验，已接受的操作不能再次执行。失败请求与命令 ID 冲突的缓存保证限于该窗口，客户端必须为新操作生成新 ID。

`MatchRecoveryValidator` 拒绝零／重复／复用标识和不合理回合；Active 存档为计数预留 2^40 分配余量，覆盖全局 ID、玩家 revision、规划序号、效果序号、规则 RNG 计数，并检查现有检查点中的 receipt／规划身份。服务端接纳前也检查此约束。它不会改写原 canonical state；纯 Kernel 接口被直接喂入 UInt64 耗尽状态时的正式终止事实仍需独立设计，不能把外围拒绝等同为内核 RuleFailure 回放。

磁盘分段、去重缓存和补发窗口已经裁剪；参与规范哈希的 CardInstances／Tombstones／CommandLog 保持完整。因此本批消除了传输与磁盘操作日志的线性累积，但不宣称无限长对局具有恒定内存。权威历史压缩仍需设计，并核验 Frozen Source、续执行与当前回放语义。

## 运行指标与诊断

- `Eota.Server.Application` Meter 提供 `eota.match.commands` 计数和 `eota.match.command.duration` 毫秒分布；同名 ActivitySource 提供 `match.command` 活动与操作类别／结果标签，不向指标标签写入牌名、命令 ID 或邀请地址。
- 每个房间私有目录的 `runtime-diagnostics.json` 每 5 秒覆盖更新：接受／拒绝／重试数量、帧数量、在线观察者、慢观察者断开、邮箱深度／峰值、去重键数量、补发占用与命中／回退、故障类别。统计从本次进程启动计数；诊断文件写入失败不终止对局。
- Actor 仅保留最近 64 条操作 trace。鉴权玩家导出的服务端部分只含该 audience 的操作类别、耗时、revision 和 trace ID；观战者拿不到玩家的规划 trace。没有匿名诊断端点，也不导出完整 MatchDiagnostics／权威状态。
- 客户端保留最近 32 条同步拒绝元数据。导出包含客户端与服务端对本席位计算的观察哈希、序号、连接状态、错误类别及该席位 trace；不含手牌、牌组、实例 ID、原始消息、token、地址 fragment 或 RNG。断线时最多等待服务端 3 秒，随后保存本机部分。

## 开发与分发

构建服务器组件：

```powershell
./tools/Publish-LocalServer.ps1
dotnet build Eota.Godot.csproj --no-restore --verbosity quiet
```

输出 `Server/win-x64/` 包含 Host、.NET 与 ASP.NET 运行时。游戏直接运行 exe，不调用 dotnet run，不依赖开发 SDK。分发时将此目录和外置 Content/Generated 随客户端一起保留。干净无 SDK 操作系统与完整游戏安装包的发布验收尚待 P11，不以开发机的成功运行替代该验收。

手工恢复私有房间（停止原进程后）：

```powershell
./Server/win-x64/Eota.Server.Host.exe --room '<房间目录>/room.json' --urls http://127.0.0.1:5075
```

旧 `--fixture` 模式保留给历史自动化验收，无席位鉴权；必须显式传入 fixture，游戏开服始终走 room 模式。
